# Kaiju Suite

A collection of Maya tools, shipped as one Maya module. Requires Maya 2025 or later.

## Install
Drag `install/drag_and_drop.py` into a Maya viewport. A **Kaiju** menu appears in the main menu bar, and the plug-in loads automatically from then on.

## Layout
```
kaiju_suite.mod          module definition
plug-ins/                thin plug-in: builds and removes the menu
scripts/kaiju_suite/
  core/                  shared internal API (no Qt, never imports tools)
  rigging/               rig module algorithms (IK, ...) and guide modules (guides/); imports only core, no Qt
  datatypes/             rig data saved to files and applied back (joints, mesh, skin, ...); imports only core, no Qt
  ui/                    menu builder and ToolWindow base class
  registry.py            discovers tools
  tools/<tool>/          one folder per tool
icons/
tests/
install/
dev/                     developer scripts, not loaded by Maya
```
Imports only flow one way: `tools` → `ui` → `core`, `tools` → `rigging` → `core`, and `tools` → `datatypes` → `core`. Tools never import each other.

## Adding a tool
1. Create `scripts/kaiju_suite/tools/<my_tool>/`.
2. Put the Maya logic in `logic.py`. Don't import Qt there; wrap edits with `@undoable` from `core.undo`.
3. Put the UI in `widget.py`, as a subclass of `ui.base_window.ToolWindow`.
4. In `__init__.py`, define a `show()` that imports the widget lazily, then a `TOOL` dict:
   ```python
   TOOL = {"name": "My Tool", "category": "Rigging", "launch": show}
   ```
5. Click **Kaiju → Reload Kaiju Suite**. The tool shows up under its category, or directly in the Kaiju menu if it has none (`category` is optional). Add `"menu": False` to keep a tool out of the menu, e.g. one that's only opened from another tool; `registry.find(name)` still finds it. Add `"startup": fn` to run something once when the plug-in loads (the Asset Library sets `ASSET` again this way).

See `tools/outliner_tool/` for a working example. Ideas for tools to build next are in [docs/tool-ideas.md](docs/tool-ideas.md).

Shared helpers live in `core/` so tools can use them without importing each other: `core.curves` (NURBS curve shapes as data, and rebuilt from it), `core.colors` (Maya's index colors), `core.matching` (vertex matching by closest point, UV or topology, used by the SkinCluster Tool and the Assembler's SkinCluster, DeltaMush and BlendShapes items), `core.nodes.unique_name`, `core.naming.opposite_name` (`L_arm` ↔ `R_arm`), `core.attributes` (custom attributes and channel lock/hide state, read as data and applied back; used by the Assembler's Attributes items), `core.checks` (scene checks for naming, unfrozen transforms, leftover history and unknown nodes, each returning problem messages; the Assembler's QC items run them; the same functions take a datatype's own checks, e.g. `datatypes.skin.CHECKS`), `core.keys` (animation and driven key curves read and written as data; used by the Assembler's Animation and Set Driven Keys items), `core.orient` (signed axes, aim/up rotation matrices and setting a joint's world rotation through its joint orient; used by the Joint Tool and the guide modules), `core.deformers` (a mesh's index in a deformer, the vertices it deforms and its weights) and `core.paths` (file paths stored relative to a build folder or `$ASSET`, see below).

## Kaiju Scripter
A simpler replacement for the Assembler (`tools/scripter/`, **Kaiju ▸ Scripter**): pick a folder and it shows its items as a tree, in the order you drag them into. Each folder keeps its order and disabled items in a hidden `.scripter/order.json`. The item kinds are in `items.py`:

- **Script** (`.py`): runs in `__main__` like the Script Editor, with `__file__` set. Double-click edits it in the Script Editor.
- **Folder**, **Separator** (`.sep`, a divider) and **Breakpoint** (`.brk`, pauses a run; right-click it ▸ **Continue** runs the rest, reading the files again).
- **Joints** (`.jnt`), **Skin** (`.skin`) and **Mesh** (`.mesh`): data published from the selection through `datatypes/`, and rebuilt or applied back when run. **New** needs a valid selection and publishes v001 straight away; **Publish...** captures the selection again as the next version; for a kind whose datatype has `CHECKS` (Skin, Joints and Mesh; a check with `publish=False` only runs in its tool) it runs them first (`items.publish_qc`) and, if any find problems, asks with a **Publish Anyway** dialog. Double-click a Skin, Joints or Mesh item to select its objects and open the SkinCluster Tool, Joint Tool or Mesh Tool (`items.TOOLS` maps a kind to its tool; `items.open_in_tool`); right-click any of them ▸ **Info...**, to see what's in it.
- **NurbsCurve** (`.curve`): NURBS curves that aren't controls (Spline IK curves, wire curves...), through `datatypes/curves.py`, and rebuilt as new curves when run, as Joints are. Same file contents as the Assembler's Curves items (`.crv`): renaming one to `.curve` makes it a NurbsCurve item. Versioned, with QC before Publish; double-click selects its curves and opens the **Curve Tool** (`tools/curve_tool/`, a QC tab on the selected curves).
- **Import File** (`.import`) and **Export File** (`.export`): hold one path, as `{"path": ...}`, relative to the item's folder when the file is inside it (`core/paths.py`). Import File imports any file Maya can import (`.ma`, `.mb`, `.fbx`, `.obj`, `.abc`...) into the root namespace; Export File exports the selection to `.ma`, `.mb`, `.fbx` or `.obj`, overwriting the file, and fails if nothing is selected. Double-click picks another file. Not versioned.
- **Selection** (`.sel`): a list of entries, as `{"entries": [{"type", "value"}...]}`: selected objects (`selected`, a list of shortest unique names or components), a name pattern (`pattern`, Maya `ls` wildcards, several separated by spaces, with an optional `node_type` from `items.NODE_TYPES`; `*` or none is any node, and Geo/Nurbs Curve/Nurbs Surface/Locator find transforms with that shape) or a selection set (`set`, nested sets expanded). Patterns and sets are looked up on every run; intermediate objects are left out. Running it replaces the selection with everything they find, in entry order without repeats, and fails naming any object, pattern or set it can't find. Double-click opens a non-modal editor for the entries with a preview. Not versioned.

**Run** (right-click) runs the selected items and folders in tree order as one undo step (Maya can't undo an Import File: it flushes the undo queue on import): a folder runs its enabled items, a selected item runs even if disabled, and the run stops at the first failure. Scripts and the Joints, Skin and Mesh items are versioned: **Publish...** copies the item into `.scripter/versions/<name>/v001...` with a description, and **Versions...** restores one (asking first if that loses unpublished edits); renaming, moving and deleting take the history along, and **Copy**/**Paste** copies it. The logic is in `logic.py` (`scan`, `create_item`, `create_data_item`, `create_file_item`, `place`, `paste`, `Runner`, ...), `items.py` (each kind and how it runs) and `versions.py` (`publish`, `restore`, `label`, ...).

## Adding an Assembler product
The Assembler lists, runs and creates "products": scripts, scenes, new scenes, folders, guides, joints, meshes, skinClusters, deltaMush, blendShapes, curves, materials, deformers (cluster, softMod, wire, lattice, nonLinear), wraps, pose correctives (poseInterpolators), poses, animation, set driven keys, constraints, connections (utility node networks), attributes, sets & display layers, control shapes, rig modules, QC checks and outputs (which save the built rig as a `.ma`, `.mb` or FBX file) today. Each one is a module in `tools/assembler/products/`.
1. Add `tools/assembler/products/<my_product>.py`. Don't import Qt there.
2. Subclass `Product` and set `name`, `extensions` and `order`. Set `runnable = True` and implement `run(path)` if it should take part in **Run All** (runnable items can also be disabled; override `can_disable` to change that). Set `menu_slot = (group, position)` to place its entry in the right-click **New** menu (dividers separate groups; leave it unset to go in a last group, or set `None` to leave it out).
3. Set `versioned = True` to give its files **Publish** and **Versions...** on the right-click menu (a window listing every version with its date and description, to Restore or Compare; `versions.changelog`). Versions are copies kept in a hidden `.versions/<file name>/` folder next to the item (`v001.py`, `v002.py`, ...); they follow the item when it's renamed or moved, and are deleted with it. Each version keeps a short description in `descriptions.json` in that folder: Publish and any `Action(..., describe=True)` (e.g. Republish) ask the user for one and run inside `versions.describing(text)`, so whatever they save with `versions.save_version` or `versions.export_into` keeps it; code that saves versions without asking (e.g. the Asset Library's starter Export Scene) passes `description=` itself. Publish saves the file as it is; override `publish(path)` to return an `Action` that does something else (Import and Export Scenes open a file browser and save the picked file's path as a new version). Return messages from `publish_problems(path)` to stop Publish before it runs; they're shown to the user in a dialog (meshes report an empty selection). Return messages from `publish_warnings(path)` for things that look wrong but shouldn't block; the user is asked whether to publish anyway (materials report missing texture files).
4. Optionally override `open(path)` for double-click, or return a `Panel` (a checklist of `Toggle`s, each with a hover tooltip and an optional `edit` Action shown as a "?" button on its row, then info lines and `Action` buttons; set `run_buttons=True` to add Run and Show Log buttons at the bottom, as QC does) from `panel(path)` to open a window on double-click instead. Set `utility` to a tool's name (e.g. `"Mesh Tool"`) to open that tool on double-click; the panel then moves to a right-click **Info** entry. Each product except Script, Folder, Separator, Import Scene, New Scene, Guides to Joints, Curves, Pose Correctives, Set Driven Keys, Connections, Sets & Layers, QC and Export Scene has a utility tool, one folder per tool under `tools/` (e.g. `tools/mesh_tool/`), listed under **Kaiju ▸ Utilities** (except the Rig Module Editor, which is only opened from the Assembler). The Assembler opens it through `registry.find(name)`, so it never imports the tool. A tool that edits the item itself adds `"open": fn(path)` to its `TOOL` dict; double-click then calls that with the item's path instead of `launch()` (the Rig Module Editor and the Guide Module Editor do this; the Assembler's own `open` shows a given build folder, and its `start_build(folder, output_path)` fills an empty one with a `build` folder holding an Export Scene; the Asset Library uses both). Override `type_name(path)` to show something other than `name` for an item in the Type column, publish messages and run logs (Rig Modules show their rig module, Guides their guide module). Return right-click `Action`s from `actions(path)`, and list `Creator`s for its entries in the **New** submenu.
5. End the module with `PRODUCT = MyProduct()`.

Builds run from the right-click menu: **Run** (the selected items) and **Run '<folder>'** (every enabled item in a folder, top to bottom; `logic.collect_steps` picks them, Qt-free).

Each run of a step is logged and saved in a hidden `.logs/<file name>.log` next to the item (right-click **Show Log** opens it). The log gets anything `run` returns as a message, Maya's output during the step (`cmds.warning`, MEL `print`, errors) and, on failure, the traceback. Call `runlog.info(message)` to log what the step did, and `runlog.warning(message)` for things it skipped: a step with warnings ends orange (Warning) instead of green, and the build goes on.

After **Run '<folder>'**, a Build Report window lists each step's status (OK / Warning / Error / Skipped), its time and a "..." button (or double-click) to open its log. The report data is Qt-free in `tools/assembler/report.py`: pass a `report.Recorder(paths)` as `on_status` to `logic.run_steps`, then read `recorder.results` (or `report.summary(results)` for plain text); the window is `report_widget.py`.

Nothing else needs registering. See `products/scene.py` for a working example.

### Storing file paths (portable paths)
A product that points to a file outside itself should store the path with `core/paths.py`, so the build folder still works when it's moved or opened on another machine. `paths.to_portable(path, root)` gives the text to store: relative to `root` (forward slashes) when the file is under it, else `$ASSET/...` when it's under the folder in the `ASSET` environment variable (pass `variables=` for others), else absolute; text that already starts with a variable is kept. `paths.resolve(stored, root)` turns that text back into a path: it expands variables and `~`, and joins relative text to `root`; absolute text, including entries written before this, is used as it is. Import Scene does this with `root` set to its **build folder**, the folder holding the `.scene` file (`scene.build_root(path)`): `scene.stored(path)` is the saved text and `scene.target(path)` the file it resolves to. Build plans export the stored text. Export Scene does the same with the file it saves to (`output.build_root(path)`, `output.target(path)`). Moving an Import or Export Scene item into a different folder of the tree changes its build folder, so a relative path then points somewhere else: publish it again.

### Rig-data products (`DataProduct`)
Products that save rig data from the scene and apply it back (Guide, Joints, Mesh, Curves, SkinCluster, DeltaMush, BlendShapes, Deformers, Wrap, Pose Correctives, Material, Pose, Animation, Set Driven Keys, Constraints, Connections, Attributes, Sets & Layers, ControlShape) subclass `DataProduct` from `tools/assembler/data.py` instead of `Product`. Their files are JSON with a header, `{"kaiju": <kind>, "format": 1, "data": <payload>}`, which `data.read(path, kind)` checks and `data.write(path, kind, payload)` writes (deterministically, so publishing unchanged content adds no version).
The save/load half lives in `scripts/kaiju_suite/datatypes/`, one module per kind of data, so tools can read and write the same files without importing the Assembler (the SkinCluster Tool's **Export/Import Weights** use `datatypes/skin.py`). Joints, Mesh, Curves and SkinCluster are there so far (Curves keeps its `.crv` extension by setting `extension` on the product, while the datatype's own is Scripter's `.curve`); the other products still hold it themselves and move one at a time. Guide items are the exception: like Rig Modules, guide modules own their file format in `rigging/guide_module/spec.py` (see Guide modules below), which also has the functions a `datatype` needs, so the Guide product sets `datatype = spec`.
1. Add `datatypes/<kind>.py` with `KIND` (the header's `kaiju` value), `EXTENSION` (one, lower case, with the dot) and these functions: `gather(nodes)`, which returns the payload for the nodes (long names) or raises; `apply(payload, info=None)`, which changes the scene and returns a message, calling `info` with one line per item applied; `selection_problems(selection)`, which returns messages when the selection can't be gathered; `describe(payload)`, the info lines for the double-click window; `nodes(payload)`, the names of the nodes (or components, e.g. `body.f[0:9]`) the payload was gathered from, such that `gather` on them gives the same kind of payload again; and optionally `compare_view(payload)` (see 4) and `CHECKS`, QC checks (`core.checks.Check`, each `fn(nodes, **options)`) that the datatype's tool shows in its QC tab (`ui/qc_tab.py`; see the SkinCluster Tool) and Scripter runs before publishing; `datatypes.run_qc(module, nodes)` runs them with the settings saved per user, shared by both. Don't import Qt, `ui`, `rigging`, the Assembler or any tool there; warn with `datatypes.warning` (`cmds.warning`), which the Assembler's run log picks up. `datatypes.save(module, path, nodes)` and `datatypes.load(module, path)` write and apply a module's files; a tool's `logic.py` wraps them (with `@undoable` for load).
2. Add the product: subclass `DataProduct` and set `name`, `order` and `datatype` (the module). `kind`, `extension`, `gather`, `apply`, `selection_problems`, `describe`, `nodes` and `compare_view` come from the module. `nodes` gives items right-click **Republish** (publish again without selecting anything: "same meshes, new weights") and **Select Objects**, and puts them in a folder's **Republish**. Products not moved yet set `kind` and `extension` and implement those methods on the class instead.
3. Everything else comes from the base class: **New ▸ <name>** creates an empty file, which a build skips; **Run** applies the file as one undo step; **Publish** gathers from the selection and saves the result as the next version via `versions.export_into(path, write_fn)` (Scene uses it too, to write the picked path); `publish_problems` returns `selection_problems()`, and `publish_warnings` returns `selection_warnings()` (none unless overridden). **Republish** (`republish(path)`) finds the names from `nodes()` with `data.resolve_nodes`, stops with one message naming any that are missing or match several nodes (`republish_problems(path)`; the window lists them first through the `Action`'s `problems`, and the double-click panel shows them too), then runs `gather` on them and saves the result as the next version, whatever is selected. **Select Objects** (`select_objects(path)`) selects the objects it finds and names the rest. Empty items get neither entry. Republish on a folder (`republish.republish_folder`) does this for every published item under it that `republishable(path)`, skipping the ones with problems, then publishes the folder. A product that overrides `actions(path)` should add `super().actions(path)` to keep it.
4. **Compare** in the Versions window comes free too: it opens a window comparing the selected version (left) with the current file (right) (`versions.compare_panel`). Selecting two items of the product adds right-click **Compare _a_ with _b_** (`versions.compare_items_panel`). Both windows show the two payloads side by side as trees (`Panel.diff`), built by `compare.tree` in `tools/assembler/compare.py`: keys matched by name, records by `name` (or `mesh`, `node`), lists of names by value, and long lists of numbers folded into one row saying how many entries changed and the largest change. Override `compare_view(payload)` to tidy a payload before it's compared, e.g. SkinCluster keys weights by influence name and drops its rest points, Joints drops `parent_index`, Mesh fills in normals and colors older files lack. It needs no scene, so test it with plain payloads. A product that isn't a `DataProduct` gets Compare by overriding `compare_files(old_path, new_path)` to return `compare.tree` rows.
5. In `apply`, skip what's missing and check the rest first, raising before changing anything. `datatypes.skip_missing(names, "meshes")` (also `data.skip_missing`) returns the missing ones and warns once naming them (Pose, SkinCluster, DeltaMush, BlendShapes, Wrap, Pose Correctives, Connections and ControlShape do this; Animation and Set Driven Keys the same by hand); `data.require_nodes(names, "influences")` instead raises one error listing them, for products where a missing node must stop the run (Material). Create nodes with `data.create_node(type, name, parent)`, which picks a free name the way Maya does (`spine_jnt` becomes `spine_jnt1`) and returns a UUID; get the current path with `data.node_path(uuid)`.

See `datatypes/skin.py` and `products/skin.py` for a working example.

### Rig modules
A rig module is an algorithm that builds part of a rig (an IK chain, ...) from parameters. The algorithm lives in `scripts/kaiju_suite/rigging/rig_module/modules/`, separate from the Assembler; the Assembler's **Rig Module** items (`.rig`) hold only the parameters, as `{"kaiju": "rigModule", "format": 1, "data": {"module": "simple_ik", "params": {...}}}` (`rigging/rig_module/spec.py` reads and writes them). Their Type column shows the rig module's name (e.g. `Simple IK`). **New** lists one entry per rig module and writes its defaults; **Run** builds the rig module as one undo step; **Publish** saves the parameters as the next version; double-click opens the **Rig Module Editor** on the file, with a form built from the rig module's parameters. Right-click **Mirror** writes the other side's item (`L_arm` -> `R_arm`, `spine` -> `spine_mirrored`) with `RigModule.mirrored(params)`, or updates it as a new version; a rig module that sets `mirrorable = False` (Root) doesn't offer it.

To add a rig module:
1. Add `rigging/rig_module/modules/<my_rig_module>.py`. Don't import Qt, `ui` or `tools` there.
2. Subclass `RigModule` from `rigging/rig_module/rig_module.py`. Set `key` (saved in the files; never change it), `name` (shown in **New** and the editor) and `params`, a tuple of `Param(key, label, kind, default, ...)`. `kind` is `"string"`, `"node"` (a scene node's name; the editor has a pick-from-selection button), `"float"`, `"bool"`, `"choice"` (with `choices`) or `"color"` (a Maya index color, 0 to 31, as in Drawing Overrides; 0 keeps Maya's default; the editor shows a drop-down of swatches). Set `required=True` for text that can't be blank and `tooltip` for the editor.
3. Implement `check(params)`, which returns messages for what stops a build in the current scene (types and required values are already checked), `create(params)`, which builds and returns what it made, and `names(params)`, the name of every transform `create` would make (groups, controls, joints, handles, constraints...), worked out without changing the scene; `outputs(params)` completes the parameters and calls it. `tests/test_rig_outputs.py` checks it against a real build, so add a case for the rig module to `tests/rig_cases.py`. `node_refs(params)` lists the scene nodes a build needs, from the filled-in `"node"` parameters; override it if other parameters name nodes (Space Switch's spaces). The Assembler's right-click ▸ **Build ▸ Check Nodes** uses both to report, before building, any node an item needs that isn't in the scene and isn't made by an earlier item. `build(params)` runs the checks, raises listing every problem before changing anything, then calls `create` inside one undo chunk. In `create`, pass each control it makes to `controls.add(control, parent=..., rig_module_set=controls.rig_module_set_name(group))` from `rigging/rig_module/controls.py` once the control has all its attributes: it tags the control for pickwalking (`parent` is the control it pickwalks up to), adds it to the rig-wide `controls_set` and to the rig module's own set (`L_arm_ik_grp` gives `L_arm_ik_controls_set`), and stores its keyable values, so **Reset Controls** can put it back.
4. End the file with `RIG_MODULE = MyRigModule()`.

Nothing else needs registering. See `rigging/rig_module/modules/simple_ik.py` for a working example, and `rigging/rig_module/modules/root.py` for one that needs no joints. `rigging/rig_module/helpers.py` has the shared pieces: checking a rig module's name, a node, a parent or a joint chain (`name_problems`, `node_problems`, `parent_problems`, `chain_problems`), and building groups, control curves (`circle`, `diamond`, `box`), a pole vector's position (`pole_position`), their color (`set_color`) and keeping the selection (`kept_selection`). `rigging/rig_module/space_switch.py` holds space switching (the `space` enum, its weights, and `switch`, which changes space without moving the control), used by the Space Switch rig module.

### Guide modules
A guide module lays out the guides for one part of a rig (a chain, a leg; a hand later) and builds them with joints that follow them live. Everything lives in `scripts/kaiju_suite/rigging/guide_module/`: the registry (`all_guide_modules()`, `get_guide_module(key)`), the `GuideModule` base class (`guide_module.py`), one file per guide module in `modules/` (Chain, Leg), `foot.py` (the foot a leg guide module hangs under its ankle, shared with the Quad Leg to come), the file format (`spec.py`) and `planar_chain.py`, the planar joint chain with live joints that guide modules are made of (it opens no undo chunk, so callers wrap it; `build_at(..., parent=joint)` hangs a chain under a joint of another chain, sharing that joint's guide). The Assembler's **Guide** items (`.guide`) hold one guide module's layout, as `{"kaiju": "guideModule", "format": 1, "data": {"guide_module": "chain", "layout": {...}}}`. **New** lists one entry per guide module (e.g. **Chain Guide**) and writes its default layout; the Type column shows the guide module's name. **Publish** reads the layout back from the selected guides (any guide, group or joint of one guide module), **Run** builds it, and right-click **Mirror** writes the other side's item with `GuideModule.mirrored(layout)`. Double-click opens the **Guide Module Editor** (`tools/guide_module_editor/`) on the file. It works like the Rig Module Editor, except that its unsaved edits are the guides in the scene: it tracks the file's guides (found by name, or picked with `<<`, then followed by UUID), **Save** writes their layout to the file without a version, **Revert** puts them back as the file has them (`GuideModule.restore`), and **Build** builds the file's guides, putting them back on the joints Delete left if there are any (`GuideModule.rebuild`). A Chain's # Mid, Aim and Up, and a Leg's Leg Aim/Up and Foot Aim/Up, change the guides live: the form shows what the guide module's `fields(layout)` lists (# Mid only if it has a `count`, one Aim and Up pair per part in `axes`), and turning a part calls `GuideModule.set_axes(group, part, aim, up)`. A **Guides to Joints** item (`.guidestojoints`, empty, not versioned), placed after the Guide items, deletes every guide in the scene when run and extracts their joints (`delete_all_guides()` in the registry, which calls each guide module's `GuideModule.extract(group)`), so the steps after it get plain joints; it checks every guide module first and changes nothing if one is broken.

To add a guide module:
1. Add `rigging/guide_module/modules/<my_guide_module>.py`. Don't import Qt, `ui`, `tools` or `datatypes` there.
2. Subclass `GuideModule` from `rigging/guide_module/guide_module.py`. Set `key` (saved in the files; never change it) and `name` (shown in **New** and the Type column, e.g. `"Hand Guide"`), and `mirrorable = False` if it has no other side.
3. Implement `default_layout(name)` (a layout for a new item; plain JSON data), `check(layout)` (messages for what stops a build in the current scene), `create(layout)` (builds under one top group named `<name>_guides_grp` and returns it), `layout(group)` (the layout as the guides are now, such that `create` on it builds the same), `mirrored(layout)` and `delete(group)` (deletes the guides, leaves their joints where they are, free of the guides, and returns them; override `check_extract(group)` to return messages for what stops that). `extract(group)` runs those checks, then calls `delete` in one undo chunk; Guides to Joints items call it on every guide module in the scene. Override `describe(layout)` for the Info lines and `nodes(layout)` if the top group isn't `<layout["name"]>_guides_grp`. `build(layout)` runs the checks, raises listing every problem before changing anything, then calls `create` in one undo chunk and tags the top group with the key, which is how Publish finds the guide module of any selected guide.
4. End the file with `GUIDE_MODULE = MyGuideModule()`.

## Headless Assembler build
Build an Assembler folder from `mayapy` with no UI, e.g. for batch rebuilds or automatic rig checks:
```
set PYTHONPATH=<kaiju_suite>/scripts
mayapy -m kaiju_suite.tools.assembler.headless <build_folder> [--new-scene] [--save out.ma]
```
It runs the folder's enabled items like **Run All** (stopping at the first failure, and saving each step's log next to it as usual), prints each step's status and messages, and exits 0 if no step failed, 1 if one did, and 2 if the folder doesn't exist. `--new-scene` starts from an empty scene; `--save` saves the scene (`.ma` or `.mb`) only if no step failed. From Python already inside Maya or `maya.standalone`, `kaiju_suite.tools.assembler.headless.build(folder, new_scene=True, save=None)` does the same and returns the result: `result.ok`, and `result.steps`, each with its `name`, `status` (`success`, `warning`, `error` or `not run`) and `messages` (`(level, text)` pairs).

## Trying a branch in Maya
Point a Maya version's line in your `kaiju_suite.mod` (in `Documents\maya\modules`) at a `kaiju_suite-dev` folder next to the main checkout. Then link that folder to whichever worktree you want to try, with no copying:
```
.\dev\use-worktree.ps1                   # list the worktrees (* = linked now) and pick one by number
.\dev\use-worktree.ps1 feature/my-tool   # link the worktree that has that branch
.\dev\use-worktree.ps1 main              # link the main checkout again
.\dev\use-worktree.ps1 -Show             # say what's linked now
```
`kaiju_suite-dev` is a directory junction (no admin rights needed). If it's a plain folder, e.g. an old copy, it's renamed to `kaiju_suite-dev.old-<time>`, not deleted. Then click **Kaiju → Reload Kaiju Suite** or restart Maya. Switch away from a worktree before removing it, or the link breaks until you switch.
